# Use @pierre/trees for the Files tool

The Files tool renders its explorer with `@pierre/trees`, not a headless tree such as `@headless-tree/react`. It already ships what a VS Code-like explorer needs (virtualised rows, ARIA tree keyboard navigation, compact folders, git status, rename, drag-and-drop and a context menu), it is backed by a company with several maintainers, and t3code uses it in production. The cost is that rows render in a shadow DOM: the tree is themed through Pierre's CSS variables, mapped from `theme.css`, plus `unsafeCSS` in one theme file, not through CSS Modules; context-menu coordinates and some events need workarounds; and it bundles Preact (about 70 kB gzipped). Because it is a 1.0 beta, the version is pinned exactly and the library stays behind our own `FileTree` wrapper, so falling back to `@headless-tree/react` means rewriting that one component. Pierre's model is a list of paths, so the backend lists one directory per expand, as t3code does, and the client adds the paths it gets back. Comparison of candidates: `.alfonz/issues/tool-bar/research/files-explorer.md`.

## Amendment: symlinks are followed

Files follows symlinks wherever they point, also out of the plane, so a folder like `.alfonz` linked in from the main checkout lists its contents instead of looking empty. Only paths that leave the plane lexically (`..`, absolute paths) are refused; the tool is browse-only, and a link inside the plane is something the user put there. Git won't check ignore rules for paths beyond a symlink, so everything under a link takes the link's own ignored status. Symlink loops need no guard because each folder is listed only when expanded. A folder that can't be listed shows a placeholder row with the reason, and Refresh tries it again.
